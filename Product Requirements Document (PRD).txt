1. Product Overview
1.1 Product vision
Build a lightweight invoicing and business management application that allows individuals, proprietors, small businesses, traders, freelancers, manufacturers, and service providers to manage their invoicing operations from a single dashboard.

Users should be able to create professional invoices, prepare estimates, manage customers and products, record payments, automate recurring invoices, and export financial reports for accounting and GST filing.

The application must use actual business logic rather than simply storing information in database tables.

For example:
- Recording a payment must automatically update the invoice's paid amount and outstanding balance.
- Creating an invoice must calculate line-item discounts, taxable values, GST, and the final amount correctly.
- Converting an accepted estimate into an invoice must preserve its line items and agreed prices.
- Generating a recurring invoice must follow its schedule without creating duplicate invoices.
- Deleting a customer must not destroy historical invoice records.
- Exporting a GST report must use saved invoice data and the applicable tax classifications, not approximate calculations from the dashboard.
The application should prioritize reliability, usability, data security, and accurate calculations over unnecessary features.
1.2 Product objectives
The primary objectives are:
1. Provide a complete invoicing workflow for Indian businesses.
2. Generate professional, printable invoice and estimate PDFs.
3. Support GST and non-GST invoicing configurations.
4. Maintain accurate customer, product, payment, and invoice records.
5. Provide useful business and tax reports with Excel-compatible exports.
6. Make the application comfortable to use on desktop, tablet, and mobile.
7. Support installation as a Progressive Web App (PWA).
8. Protect business and financial data using professional security practices.
9. Keep the interface consistent with the existing ToolLab website.
10. Make future expansion possible without requiring a complete rewrite.

2. Product Principles
The application must follow these principles throughout development.
2.1 Simplicity first
Show users the information they need to complete their work. Avoid unnecessary widgets, animations, excessive colors, complicated navigation, and decorative elements that do not improve usability.
2.2 Real business logic
Every financial operation must have a defined rule, validation process, and expected outcome.

For example, a payment must be associated with an actual invoice or another explicitly supported receivable. A payment should never be recorded against an arbitrary customer balance without the relevant transaction details.
2.3 Financial accuracy
All monetary calculations must be performed on the server using decimal arithmetic or integer paise, with consistent rounding rules. JavaScript may provide previews, but the server must recalculate and validate every financial transaction.
2.4 Historical accuracy
Invoices that have been formally issued must retain their original financial details even when a customer changes their address or a product's price changes later.
2.5 Security by default
Users must only access business records they are authorized to access. Authentication alone is not sufficient. Every database operation must also enforce record ownership and permissions.
2.6 Responsive by design
The application must adapt to mobile, tablet, and desktop layouts without making important actions inaccessible or forcing users to interact with oversized tables on small screens.
2.7 Maintainable architecture
Business calculations, database access, authentication, PDF generation, and interface rendering must be separated into logical components.

No major business rule should depend on duplicated logic scattered throughout multiple pages.

Use Composer to manage maintained PHP dependencies where supported. Lock dependency versions in composer.lock.
3.2 Application architecture
Use a modular, server-rendered PHP application with a clear separation between presentation, business logic, and persistence.

A suitable request flow is:

Browser → PHP route/controller → Authentication and authorization → Validation → Business service → Repository/PDO → MySQL → Response

PDF and Excel generation should use the same validated business services and database records as the normal application.

The frontend must never be the source of truth for invoice totals, payment balances, permissions, or document numbering.
Architectural requirements
- Use a single application bootstrap for configuration and shared services.
- Separate public routes from authenticated routes.
- Separate controllers, services, repositories, and templates.
- Use database transactions for financial operations involving multiple database changes.
- Enforce business ownership at the query and service layers.
- Centralize financial calculation rules.
- Use reusable UI components and templates.
- Avoid duplicating the same calculation in PDF templates, reports, and invoice forms.
- Keep secrets and database credentials outside publicly accessible directories.
- Do not require Node.js at runtime.
- Do not introduce microservices unless a demonstrated requirement justifies them.
3.3 Multi-tenant architecture
The application should be designed for multiple independent business accounts from the beginning, even if the first release has relatively few users.

A user may own or belong to a business workspace. Each workspace contains its own customers, products, invoices, estimates, recurring schedules, payments, and reports.

Every business-owned table must include a business_id or have an explicit, secure relationship to a business-owned parent record.

For example:
- Business A must never retrieve Business B's invoices.
- A user must not access another business's customer by modifying a URL ID.
- Exporting a report must apply the same business scope as viewing the report.
- PDF downloads must verify that the requested invoice belongs to an authorized business.
Use a centralized authorization service and ownership checks for every relevant operation.

Initial scope: One business workspace per registered user is a reasonable starting point. The schema should allow a future user to belong to multiple workspaces without redesigning the whole system.
4. User Accounts and Authentication
4.1 Registration
The registration page must include:
- Full name
- Email address
- Password
- Confirm password
- Terms and privacy notice acknowledgement, where applicable
- Create account button
- Sign in link
- Continue with Google button
Registration rules
1. Validate all fields on the server.
2. Normalize email addresses consistently.
3. Enforce a unique database constraint for the normalized email.
4. Require an appropriately strong password.
5. Store passwords using PHP's password_hash().
6. Never store plaintext passwords or reversible password encryption.
7. Prevent duplicate account creation.
8. Rate-limit registration attempts.
9. Provide a secure email verification workflow.
10. Create the initial business workspace only after successful account creation, according to the chosen verification workflow.
Use password_verify() for password authentication and password_needs_rehash() when appropriate.

Reference: PHP password hashing documentation
4.2 Login
The login page must support:
- Email and password
- Continue with Google
- Forgot password
- Remember-me behavior, if implemented securely
- Sign out
Security requirements
- Use HTTPS throughout the application.
- Regenerate the PHP session ID after successful authentication.
- Use Secure, HttpOnly, and appropriate SameSite session cookies.
- Set session inactivity and absolute lifetime policies.
- Rate-limit failed login attempts.
- Return generic authentication errors that do not reveal whether an email exists.
- Invalidate the server-side session on logout.
- Protect state-changing requests against CSRF.
- Do not store session tokens in browser local storage.
- Do not implement permanent login by keeping a session ID alive indefinitely.
PHP's official documentation describes session management and related security considerations. PHP session security documentation
4.3 Google sign-in
Implement Google sign-in using Google's supported OAuth 2.0 / OpenID Connect flow.

Requirements:
1. Register the application in Google Cloud.
2. Configure authorized redirect URIs.
3. Use the official Google identity flow or a maintained server-side OAuth library.
4. Validate the authorization response, state, issuer, audience, signature, and expiration as appropriate to the selected flow.
5. Use a unique, verified Google account identifier as the external identity key.
6. Do not use an unverified email claim to establish account ownership.
7. Associate a Google identity with an existing account only through a verified, secure account-linking workflow.
8. Do not automatically merge accounts merely because their displayed email addresses match.
9. Keep client secrets outside the public web directory.
10. Provide a clear error message if Google authentication fails.
A user who signs in through Google should have access to the same application features as a user who signs in with an email and password.
4.4 Password recovery
The password reset workflow must:
- Allow a user to request a reset using their email.
- Always show a generic confirmation message.
- Generate a cryptographically secure, single-use reset token.
- Store only a hash of the token.
- Give the token a short expiration period.
- Invalidate the token after successful use.
- Rate-limit reset requests.
- Invalidate existing sessions or provide a clear session-revocation policy after a password reset.
4.5 Account settings
Users must be able to:
- Update their name.
- Change their email through a verification workflow.
- Change their password.
- Connect or disconnect Google sign-in when safe to do so.
- View active sessions where supported.
- Sign out of other sessions.
- Request account deletion.
Account deletion must not silently destroy legally important issued invoice records. Provide an appropriate data-retention and export workflow before deleting or anonymizing data, subject to applicable law.

7.3 Invoice lifecycle
Recommended statuses:
Status	Meaning
Draft	Work in progress, not formally issued
Issued	Officially issued to the customer
Partially Paid	Some amount has been received
Paid	The outstanding balance has been settled
Overdue	The invoice has an outstanding balance after its due date
Void	An issued document has been formally voided under the application's controlled process


The overdue state can be derived from the due date and outstanding balance rather than permanently stored as the only source of truth.
Important rules
- Draft invoices may be edited or deleted by an authorized user.
- Issued invoices must not be silently rewritten or deleted.
- An issued invoice with an incorrect value should be corrected through an appropriate documented adjustment process.
- Voiding an invoice must require confirmation and a reason.
- A voided invoice must remain available for audit and historical reference.
- Issuing an invoice must record its issue timestamp and the user who issued it.
- A duplicate action must create a new draft with a new invoice number assigned according to the numbering policy.
- Invoice numbering must remain unique within the configured business and financial year.
Legal and accounting consideration: The application must distinguish between a draft, an issued invoice, a voided document, and a legally appropriate credit or debit note. It must not treat a database deletion as a valid substitute for an accounting adjustment.

The PDF should include:
- Business logo

- GSTIN, where applicable
- Invoice number and date
- Due date
- Customer information
- Billing and shipping addresses, as applicable
- Product or service descriptions
- HSN/SAC information
- Quantities and units
- Unit prices
- Discounts
- Taxable values
- GST breakdown
- Total amount
- Amount in words, where supported
- Payment details
- Notes and terms
- Authorized signature area, where appropriate
- Applicable document designation
The PDF should have a professional A4 layout by default.

Long invoices must paginate correctly. Table headers should repeat where supported, and totals should not overlap line items or footers.
PDF behavior
- Generate PDFs from server-validated, saved invoice records.
- Escape all customer and product content before rendering HTML.
- Prevent untrusted content from loading arbitrary remote resources.
- Restrict access to the requested business's documents.
- Use stable filenames, such as INV-2026-0001.pdf, without exposing internal database IDs.
- Allow download and printing.
- Keep issued document snapshots unchanged when the underlying catalog or customer profile changes.
If PDF generation fails, show a useful error and retain the invoice. A PDF failure must not cause a second invoice to be issued.

8.5 Convert estimate to invoice
Provide a Convert to Invoice action for eligible estimates.

1. Verify that the estimate belongs to the current business.
2. Verify that the estimate is eligible for conversion.
3. Create a new invoice draft using the estimate's saved customer and line-item details.
4. Preserve agreed quantities, prices, and discounts.
5. Revalidate tax treatment against the required issuance rules.
6. Assign an invoice number according to the invoice numbering policy.
7. Store a relationship between the original estimate and the new invoice.
8. Prevent accidental duplicate conversion.
9. Allow an authorized user to review and issue the resulting invoice.
Conversion should not automatically mark an invoice as paid or issue it without the appropriate action.

9.3 Generation logic
The recurring engine must:
1. Identify active recurring profiles whose next run is due.
2. Acquire a safe processing lock or use another concurrency-safe method.
3. Check whether an invoice has already been generated for the scheduled occurrence.
4. Create the invoice in a database transaction.
5. Store the scheduled occurrence and resulting invoice relationship.
6. Update the next scheduled date only after successful processing.
7. Record failures and retry them according to a defined policy.
8. Avoid duplicate invoice creation when a scheduled task runs more than once.
Use a database uniqueness constraint or equivalent idempotency mechanism for each recurring profile and scheduled occurrence.
Shared-hosting implementation
If the host supports cron jobs, use a scheduled PHP CLI task or a protected web-triggered task with strong authentication and locking.

Do not assume a continuously running worker is available on shared hosting.

If automatic scheduling cannot be configured reliably, the application must show the next scheduled run and provide a manual generation action.
9.4 Important tax rule
Recurring invoice generation must not blindly reuse historical tax settings if relevant tax information has changed.

Each generated invoice must preserve the applicable document details and validate the configured tax treatment before issuance.

Provide a manual-review mode for businesses that need to approve invoices before they are formally issued or emailed.

Fields:
- Customer
- Receipt date

- Payment method
- Transaction reference
- Bank or account details, optional
- Internal notes
- Invoice allocation
Supported payment methods:
- Cash
- Bank transfer
- UPI
- Cheque
- Debit card
- Credit card
- Other
The application should allow one receipt to be allocated across multiple invoices belonging to the same customer.

It should also allow multiple partial payments against a single invoice.
Example
Suppose a customer receives an invoice for ₹25,000.
Transaction	Amount
Invoice total	₹25,000
First payment	₹10,000
Second payment	₹5,000
Total allocated payments	₹15,000
Outstanding balance	₹10,000


After the first payment, the invoice becomes partially paid. After the second, it remains partially paid.

The status becomes Paid only when the valid outstanding balance reaches zero under the application's rounding rules.
12.4 Payment validation
The system must:
1. Verify that the customer belongs to the current business.
2. Verify that each allocated invoice belongs to the same business and customer.
3. Prevent allocation beyond the available unallocated receipt amount.
4. Prevent allocation beyond an invoice's outstanding balance, unless a separately defined credit or overpayment workflow permits it.
5. Prevent invalid negative payments.
6. Validate payment dates and monetary precision.
7. Record the user and timestamp for each transaction.
8. Use a database transaction when recording the receipt and its allocations.
9. Recalculate invoice balances using saved transaction data.
10. Prevent duplicate submissions from creating duplicate receipts.
Do not store the invoice's paid amount as an independently editable field. Calculate it from valid payment allocations, or maintain a carefully controlled derived balance that can be reconciled against those allocations.
12.5 Payment editing and deletion
Financial records need controlled correction workflows.
- Draft or unconfirmed receipts may be edited.
- Posted receipts must not be silently deleted.
- Incorrect posted receipts should be reversed through a documented operation.
- Reversals must retain the original receipt and reason for reversal.
- Reversal must remove the effect of the original allocation without erasing history.
- Reports must exclude reversed receipts from valid collections.
- Editing a posted receipt must preserve an audit trail.

- Receipt number

- Amount received

- Related invoice numbers

- Remaining balance, if applicable
The receipt must not claim that an invoice is fully settled when only part of its amount has been paid.

15. Core Financial Business Logic
This section is critical. The application must use a single calculation engine for invoice forms, stored documents, PDFs, and reports.
15.1 Monetary precision
Use MySQL DECIMAL types or integer paise for monetary values. Do not use floating-point database columns for financial amounts.

Suggested conventions:
- Monetary amounts: DECIMAL(15,2)
- Unit prices: DECIMAL(15,4) where additional precision is needed
- Quantity: DECIMAL(15,3) or a suitable configurable precision
- Tax rates: DECIMAL(7,4) or an appropriate precision
Choose precision based on the supported business workflows and accounting requirements.

All calculations must follow a documented rounding policy. Do not round at inconsistent stages in different modules.
15.2 Line-item calculation
For a standard line item:

Gross line value = Quantity × Unit price

If the discount is a percentage:

Discount amount = Gross line value × Discount percentage ÷ 100

Then:

Taxable line value = Gross line value − Applicable pre-tax discount

The applicable tax is calculated from the taxable value and the selected tax treatment.

For example, for a taxable item with a gross value of ₹10,000 and a 10% pre-tax discount:
Calculation	Amount
Gross value	₹10,000
Discount	₹1,000
Taxable value	₹9,000
GST at 18%	₹1,620
Total	₹10,620


This example assumes the discount reduces taxable value and the full 18% rate applies to the item.
15.3 Tax calculation
For a standard intra-state taxable supply with an applicable total GST rate of 18%, the usual presentation is:
- CGST: 9%
- SGST: 9%
For a standard inter-state taxable supply with the same total rate:
- IGST: 18%
This is an illustrative calculation, not a universal rule for every transaction.

The system must determine the appropriate tax treatment from the relevant business configuration, supply details, and applicable rules.
15.4 Invoice-level discount
If an invoice-level discount is applied:
1. Determine the eligible line-item values.
2. Allocate the discount according to the documented allocation method.
3. Recalculate the taxable value of each affected line.
4. Recalculate applicable taxes.
5. Apply the documented rounding policy.
6. Reconcile any rounding difference.
Do not subtract a discount from the final amount without determining its correct tax treatment.
15.5 Invoice totals
The final invoice total must be derived from the validated line items, discounts, taxes, and applicable additional charges.

Conceptually:

Invoice total = Sum of taxable values + Applicable taxes + Other charges − Applicable post-tax adjustments

Any rounding adjustment must be separately identifiable.

The calculation engine must define exactly which values are rounded at line level and which are rounded at document level.
15.6 Partial payments
For each invoice:

Outstanding balance = Issued invoice total − Valid allocated payments − Applicable credit adjustments

The implementation must ensure that a credit adjustment reduces the receivable only when it is valid under the supported document workflow.

Voided invoices, reversed payments, and drafts must not be included as if they were valid transactions.
15.7 Credit notes and debit notes
A full accounting product should eventually support credit notes and debit notes.

For the first release, decide whether to include a limited adjustment workflow or explicitly defer these documents.

If they are deferred, the application must not pretend that editing or deleting an issued invoice is a compliant substitute.
15.8 Document numbering
Invoice and estimate numbers must be:
- Unique within their defined scope.
- Generated on the server.
- Resistant to concurrent requests.
- Associated with the correct business and financial year.
- Preserved after issuance.
- Auditable.
Use a database-backed counter or equivalent transactional strategy rather than generating a number from MAX(invoice_number) + 1.

The database must enforce the relevant uniqueness constraints.

18. Security Requirements
Security is a core requirement because the application stores business identities, customer details, financial documents, and payment information.

The implementation should follow established guidance such as the OWASP Cheat Sheet Series.
18.1 SQL injection protection
- Use PDO prepared statements for data values.
- Never construct SQL by concatenating untrusted user input.
- Use allowlists for dynamic column names and sorting directions.
- Validate identifiers and pagination parameters.
- Use a database account with only the privileges the application needs.
- Do not expose database error messages to users.
Reference: OWASP SQL Injection Prevention Cheat Sheet.
18.2 Cross-site scripting
- Escape output according to its HTML, attribute, URL, or JavaScript context.
- Treat customer names, product descriptions, notes, and uploaded filenames as untrusted.
- Avoid unsafe HTML insertion in JavaScript.
- Use a Content Security Policy where compatible with the application's scripts and integrations.
- Never assume that database-stored text is safe to render.
18.3 CSRF protection
All state-changing operations must require CSRF protection.

This includes:
- Creating and editing invoices
- Issuing and voiding documents
- Recording and reversing payments
- Editing customers and products
- Updating settings
- Deleting or archiving records
- Changing authentication settings
Use server-validated CSRF tokens. SameSite cookies provide an additional defense but are not a replacement for request validation.
18.4 Authorization
Every sensitive request must verify:
- The user is authenticated.
- The user belongs to the selected business.
- The user has permission to perform the requested action.
- The requested record belongs to that business.
- The requested operation is valid for the record's current state.
Never rely only on hidden buttons, client-side checks, or unguessable URLs.
18.5 File upload security
If the application supports business logos, signatures, or other uploads:
- Restrict file types and sizes.
- Validate the actual file content, not just the extension.
- Generate server-controlled filenames.
- Reject dangerous file formats.
- Store files outside the public directory when possible.
- Prevent executable uploads.
- Restrict file access.
- Process images safely before embedding them in PDFs.
18.6 Payment data
The first release should record payments rather than process card payments directly.

Do not store card numbers, CVVs, banking passwords, UPI PINs, or other payment authentication secrets.

For future online payment collection, integrate a reputable payment gateway and use its supported hosted checkout or tokenized flow.
18.7 Audit logging
Record important operations, including:
- Login and authentication events
- Business profile changes
- Invoice issuance
- Invoice voiding
- Estimate conversion
- Payment recording
- Payment reversal
- Document numbering changes
- Tax setting changes
- User and permission changes
- Data export events
Audit entries should contain the actor, business, action, target record, timestamp, and relevant non-sensitive context.

Do not write passwords, session tokens, OAuth tokens, SMTP credentials, or unnecessary sensitive customer data to logs.
18.8 Rate limiting
Apply rate limits to:
- Login
- Registration
- Password reset
- Email verification
- Google sign-in callbacks
- Email sending
- Export generation
- Other sensitive endpoints
Rate limiting should not depend entirely on a user-supplied identifier.
18.9 Error handling
Production mode must:
- Disable public display of PHP errors.
- Log diagnostic information privately.
- Show understandable error messages.
- Roll back incomplete financial transactions.
- Avoid revealing database credentials, filesystem paths, or stack traces.
- Provide a request reference for investigating unexpected failures.

21.1 Backend performance
- Use indexed database queries.
- Avoid loading every invoice or customer into memory.
- Implement server-side pagination.
- Avoid unnecessary database queries inside loops.
- Use transactions for related financial operations.
- Cache suitable non-sensitive configuration where useful.
- Avoid generating every PDF during page rendering.
- Limit export row counts and memory usage.
- Use efficient queries for dashboard summaries.
21.2 Frontend performance
- Load only the JavaScript required for the current page.
- Avoid unnecessarily large libraries.
- Use optimized icons and images.
- Minimize layout shifts.
- Avoid heavy animations.
- Keep form interactions responsive.
- Prevent duplicate form submissions.
- Display loading indicators for long-running operations.
21.3 Performance acceptance targets
Under a representative test dataset and reasonable hosting conditions:
- Typical page requests should generally complete within 1 second at the application-server level.
- Invoice and customer lists should load without fetching the entire database.
- Common actions should provide prompt feedback.
- Large exports should not block unrelated requests unnecessarily.
- Dashboard totals should remain correct after filtering or pagination changes.
These are engineering targets, not guarantees. Actual results depend on the hosting environment, database size, network latency, and third-party services.
22. Notifications and Email
The application should support transactional email for important business workflows.
22.1 Email types
- Email verification
- Password reset
- Invoice delivery
- Estimate delivery
- Payment receipt
- Payment reminder
- Recurring invoice generation notification
- Security-related notifications
22.2 Invoice email workflow
The user should be able to send an invoice directly from the invoice detail page.

The workflow should:
1. Verify that the invoice is eligible to send.
2. Verify that the recipient address is valid.
3. Generate or retrieve the appropriate PDF.
4. Send the email through the configured provider.
5. Record the delivery attempt and result.
6. Display success or failure.
7. Allow a controlled retry.
A successful SMTP submission does not guarantee that an email reached the recipient's inbox. The interface should distinguish between submission success, delivery confirmation where available, and failure.
22.3 Payment reminders
Allow reminders to be sent manually.

Automated reminders may be enabled through scheduled jobs if the hosting environment supports them.

The system must avoid repeatedly sending reminders after an invoice has been paid or voided.
23. Backup, Recovery, and Data Retention
23.1 Backup requirements
The business must have a documented backup strategy covering:
- Database
- Uploaded business assets
- Relevant document snapshots
- Application configuration required for recovery
Store backups separately from the public web root.

Where possible, maintain an additional protected copy outside the hosting account.
23.2 Backup security
- Restrict access to backups.
- Do not expose SQL dumps through public URLs.
- Encrypt backups when practical.
- Protect backup credentials.
- Define retention periods.
- Avoid logging secrets.
- Keep backups separate from temporary export files.
23.3 Recovery requirements
Document a restore procedure that includes:
1. Preparing a clean application environment.
2. Restoring the database.
3. Restoring necessary files.
4. Reapplying appropriate permissions.
5. Verifying configuration.
6. Checking invoice and payment consistency.
7. Testing authentication and authorization.
8. Confirming that the application is operational.
Perform periodic restore tests. A backup that has never been tested should not be treated as a proven recovery mechanism.
23.4 Data retention
Define retention rules for:
- Issued invoices
- Voided invoices
- Payments and reversals
- Audit logs
- Email logs
- User account data
- Temporary exports
- Backups
The application should not automatically delete historical financial records simply because a customer or user account is closed.

Retention periods must be configurable or documented according to applicable legal requirements.

31. Final Implementation Instructions
The following instructions should guide the development agent or developer who implements this PRD.
31.1 Analyze before coding
Before modifying or creating files:
1. Inspect the existing ToolLab website at toollab.in.
2. Review the current branding, logo, colors, typography, spacing, and visual conventions.
3. Confirm the actual hosting environment and available PHP extensions.
4. Confirm the supported PHP and MySQL versions.
5. Identify available Composer support.
6. Finalize the project structure.
7. Review this PRD and resolve any conflicting implementation assumptions.
8. Document architecture decisions before implementing major financial workflows.
Do not blindly copy the public ToolLab website's structure. Reuse the brand's design language while designing an interface appropriate for a business application.
31.2 Implement real functionality
Do not create a frontend-only prototype and describe it as a completed application.

Every primary action must work with persistent database records.

Examples:
- Create Invoice must save a validated invoice.
- Issue Invoice must assign or finalize a unique document number and preserve the issued record.
- Download PDF must generate the actual document.
- Record Payment must save the receipt and allocations.
- Export Excel must generate a valid spreadsheet containing real filtered records.
- Convert to Invoice must create a linked invoice draft.
- Delete must follow the relevant document lifecycle and retention rules.
- Save Settings must persist and validate the configuration.
Do not use placeholder buttons, fabricated statistics, simulated payments, or hardcoded customer records in production.
31.3 Centralize business rules
Implement reusable services for:
- Invoice calculations
- GST calculations
- Document numbering
- Invoice issuance
- Payment allocations
- Payment reversals
- Estimate conversion
- Recurring invoice generation
- Report calculations
- PDF generation
- Spreadsheet generation
Controllers should coordinate operations rather than contain the full financial calculation logic.
31.4 Prioritize financial correctness
Before developing decorative dashboard components or advanced settings, ensure that:
- Invoice calculations are correct.
- Tax treatment is configurable and validated.
- Invoice numbering is reliable.
- Historical documents remain unchanged.
- Payment allocations are accurate.
- Voiding and reversal workflows preserve history.
- Report totals reconcile with the saved transactions.
- Cross-business access is prevented.
31.5 Do not overcomplicate the interface
Use a clean layout, a limited color palette, reusable components, and straightforward navigation.

The application should be easy to understand without training.

Every major page should have one clear primary action, predictable interactions, helpful empty states, and understandable error messages.
31.6 Verify before deployment
Do not deploy based solely on a successful homepage load.

Run the documented test suite and verify the complete invoice lifecycle, PDF generation, payment recording, report exports, account isolation, and mobile usability.

Production launch must be blocked by unresolved critical security vulnerabilities, incorrect financial calculations, duplicate document numbering, or unauthorized access to business records.
